# Scope panel — raw scoper proposals

Verbatim output of the three divergent scopers (repo-fit / ambitious / minimalist).
Recorded as the provenance trail; the finalized scope may differ.

## Scoper: `fit`

**Fit verdict:** `clean`

This is an entry point over library code that is already built, already tested and already documented — no new dataset, no new table, no parser change, no ADR contradiction. The pattern it copies exists twice and is explicitly self-describing: `src/ootp_ai/reports/__main__.py:1-11` (argparse, one subcommand, `main()` thin over a testable `render(settings, ...)`, exit 0/1/2) and `src/ootp_ai/catalog/__main__.py:82-115` (same shape, `generate(settings, ...)`). ADR 0005's question does not even open here: the command produces no artifact of its own, it drives the parser->bronze path that is already on the 'yes, it changes when the league is simulated' side, so the five dataset contracts (grain/keys/coverage/update semantics/pattern) stay exactly where `src/ootp_ai/contracts/tables.toml` already declares them and this work must not add a ninth table. The parser obligations are likewise already discharged — `parser/header.py` refuses a non-25 header on the way in via `take_snapshot` -> `_read_sim_date` and again per file in `ingest._describe` (`ingest.py:481-501`), and `check_decoded`/`check_sim_dates` (`ingest.py:235-278`) refuse a moved layout or a mixed snapshot — so the command's only parser-facing job is to surface those refusals as an exit code rather than a traceback.

Three of the request's own assumptions need correcting, and none of them forces a redesign — which is why this is 'clean' and not 'reshape':

1. **No WRITERS allowlist entry is needed.** The request's Scope Signals list 'the writer-allowlist entry the new module needs'. `tests/test_read_only.py:361-372` scans each module's *own source text* for `.write_text(`/`.write_bytes(`/`.mkdir(`/`os.makedirs`/a write-mode `open(`. A module that only calls `take_snapshot`, `parse_snapshot`, `land_snapshot`, `connect_warehouse` and `print` contains none of those tokens — `snapshot.py:205` does the `mkdir(parents=True)` and it is already allowlisted, and `config._root` deliberately does not create its roots (`config.py:196-197`). So the correct outcome is the *opposite* of what the request expects: the new module must stay off `WRITERS`, and that absence is worth asserting.

2. **`--save-id` does not mean on the ingest side what it means on the render side.** `reports render --save-id` is a warehouse key looked up in `ingest_run` (`reports/resolve.py:97-122`). An ingest command needs a *save on disk*, and `Settings` exposes exactly three (`config.py:99-108`: `managed`, `truth_save`, `probe_save`). The two can still share one vocabulary because `SaveRef.save_id` is `to_save_id(league)` (`config.py:82-84`) — the same string the warehouse keys on — so `--save-id` should resolve against the configured refs by name and never accept a filesystem path.

3. **The naive composition auto-allocates instead of refusing.** `take_snapshot` with `ingest_seq=None` allocates the next free filesystem sequence and never raises; `SnapshotExists` only fires when a sequence is named explicitly (`snapshot.py:189-201`, pinned by `tests/test_snapshot_semantics.py:276-284`). So `land = snapshot + parse + land` composed the obvious way silently produces a duplicate 46 MB copy and a duplicate ~301,000-row landing every time the operator re-runs out of habit — the exact failure the request's Open Question 3 names. The default has to be chosen deliberately.

One further gap the request does not mention and the desired outcome depends on: **`ensure_tables` also has no caller outside the tests.** `ops/mysql-bootstrap.sql` creates schemas, the app user and grants — no tables (lines 23-63). `warehouse/load.py:169` `ensure_tables` is called only from `tests/fixtures/warehouse.py:93`. So on a fresh machine the eight declared tables exist *only because someone ran the gamedata suite*, and 'one documented command followed by `reports render` produces a roster page' fails at the first INSERT unless the command creates them. The test suite is doing two pieces of production work here, not one.

No duplication with anything that exists: `reports/__main__.py` and `catalog/__main__.py` both only read a landing. `incremental-loading` claims the two-date proof and the operator's written procedure and explicitly does not claim the vehicle. `open-front-office`'s Phase B lander is a GM write channel for `gm/`, not a warehouse loader.

### Goals

- Give the operator one documented command that takes a configured save from disk to a landed bronze snapshot — snapshot, parse, land — and prints the `(save_id, sim_date, ingest_seq)` triple it created, so a landing and a later `reports render` can be tied together in a `gm/decisions/` record.
- Site it as `uv run python -m ootp_ai.warehouse land`, using the existing `warehouse/` package (its `__init__.py` already describes itself as owning 'bronze landing') so nothing is restructured and no speculative directory is created — CLAUDE.md forbids the latter, and promoting `ingest.py` to a package would churn seven test modules plus `warehouse/load.py` for no gain.
- Make the pipeline's game-touching half a single named function — `read_save(save, *, settings) -> ParsedSnapshot`, composing `ingest_save` and `parse_snapshot` in `src/ootp_ai/ingest.py` — with exactly three callers: the new command, `tests/test_read_only.py`'s AC11 diff, and `tests/fixtures/warehouse.py`. One name means the operator's path is the path ADR 0001's manifest diff brackets.
- Resolve the target by name from `.env`, never from a path argument: `--save-id` matches `SaveRef.save_id` across `settings.managed` / `truth_save` / `probe_save`, defaults to the managed league exactly as `reports render` and `catalog` do, and makes rehearsing against the disposable Challenge twin (SD-20) a first-class option rather than an edit to `.env`.
- Surface ADR 0021's append-only semantics without softening them, and settle the operator-facing default deliberately: a second landing of a `(save_id, sim_date)` that already has one refuses by default and names both the triple it found and the flag that overrides it; the override takes the next `ingest_seq` and leaves the earlier landing byte-identical.
- Make a fresh clone work end to end: `ensure_tables` runs before anything is copied, so 'uv sync -> bootstrap -> one command -> `reports render`' produces a roster page on a machine where `pytest` was never run.
- Retire the gap: replace README.md's 'There is no ingest command' blockquote (lines 128-134) with the command, and re-point `tests/fixtures/warehouse.py::landed_probe` onto the shared function so the fixture and the operator cannot drift.
- Keep every machine-specific absolute path out of stdout: report the snapshot location relative to the configured snapshot root, because the operator pastes this output into `gm/`, which is tracked, public, and scanned for drive letters by `tests/test_no_leaks.py:37-41`.

### Non-goals

- Rendering anything. `reports render` is the render entry point and `python -m ootp_ai.catalog` the catalog's; this command lands and prints, and writes no file of its own.
- The two-sim-date proof and the operator's sim-forward-and-re-land procedure — both are claimed by `requests/feature-requests/incremental-loading/`, whose acceptance turns on creating a second date rather than finding one. This request builds the vehicle it drives.
- Any change to landing semantics. `ingest_seq` allocation, the `IngestRunExists` refusal, the primary key that actually prevents an overwrite, and the deadlock retry (`warehouse/load.py:232-250`) are settled by ADR 0021 and are exposed here, not renegotiated. No `--force` that overwrites a triple, no upsert, no DELETE path in `src/`.
- A ninth table, a new column, a contract edit, or any change to `src/ootp_ai/contracts/tables.toml` — `docs/warehouse-catalog.md` must be byte-identical after this work (`tests/test_catalog.py` would say otherwise).
- Any parser change. Every byte this moves is already read by walkers under test.
- Scheduling, watching, daemonising or automating a run. The operator decides when a save is worth landing.
- Anything that writes to a save, or a `--snapshot-root` / `--saved-games` flag that would let an operator aim the pipeline at an unfenced location (ADR 0001, and `config._root` is where write roots get fenced).
- A `[project.scripts]` console entry point. `uv run python -m ootp_ai.<package>` is the established invocation for both existing commands (README.md:117-118).
- Landing more than one save per invocation, a `--dry-run` that parses without landing, and progress output for the ~2.2 s parse.
- A GM-facing surface. This is an operator/umpire command; ADR 0016 keeps the GM on reports, and landing a save costs no GM action.
- Pulling dbt in. ADR 0004's deferral stands; this touches bronze landing only.
- Retention, pruning or a purge helper in `src/` — ADR 0021 §3 and `warehouse/load.py:69-74` both name a convenience purge as the way append-only stops being true.

### Core scope

- `src/ootp_ai/warehouse/__main__.py` — the new entry point, invoked `uv run python -m ootp_ai.warehouse land`. Structured exactly like its two predecessors: a thin `main(argv) -> int` that resolves settings, parses args, catches and reports, and a testable `land(settings, *, save_id=None, again=False) -> IngestRun` that a test can call without a subprocess (the shape `tests/test_reports.py:93-106` and `tests/test_catalog.py:176-181` both depend on).
- `read_save(save, *, settings) -> ParsedSnapshot` added to `src/ootp_ai/ingest.py` — the whole game-touching half under one name: `parse_snapshot(ingest_save(save, settings=settings).snapshot)`. Three callers, one path. This is what makes Open Question 5 answerable honestly: AC11's manifest diff brackets the function the operator actually runs, while landing (MySQL) stays outside ADR 0001's guard.
- Target resolution by logical name. Build the map `{ref.save_id: ref}` over `settings.managed`, `settings.truth_save`, `settings.probe_save` (skipping the `None`s CI and a fresh clone will have); `--save-id` selects, absent it the managed league wins. An unknown id exits 2 naming what *is* configured, in the manner of `reports/resolve._nothing_landed_message`. No path argument is accepted, ever.
- Fail-fast ordering, stated because it is not the natural order: settings -> target -> warehouse connection -> `ensure_tables` -> prior-landing check -> `read_save` (snapshot + parse) -> `land_snapshot`. A machine with MySQL down must fail before ~46 MB is copied, not after; a snapshot with no landing behind it is an orphan the next run steps past.
- `ensure_tables(connection)` on every run, before the copy. `ops/mysql-bootstrap.sql` creates schemas and grants only (lines 23-63) and `warehouse/load.py:169` is currently called from one test fixture, so without this the fresh-clone story dies at the first INSERT. `ensure_tables` creates and never replaces, so it is safe to run every time.
- The append-only surface, with the default decided: if `(save_id, sim_date)` already has an `ingest_run` row, refuse — naming the existing triple, the landed date, and the flag — unless the operator passes the deliberate-second-look flag, which lands at the next sequence beside its predecessor. Refusing is the safe half of ADR 0021; auto-allocating on a habitual re-run is a 46 MB copy plus ~301,000 rows (264,095 of them `bronze_name`) that nobody meant to create.
- Sequence policy, stated rather than defaulted: the operator's snapshot is **durable** (it goes under `settings.snapshot_root`), so the filesystem-allocated `ingest_seq` is passed explicitly to `land_snapshot` — `warehouse/load.py:203-217` is explicit that this is what keeps the snapshot store and the warehouse naming the same attempt, and it makes `IngestRunExists` a real backstop under the pre-flight check rather than dead code.
- The stdout contract: the triple, the per-table row counts from the returned `IngestRun` (which `_check_counts` verified against the schema inside the transaction), and the snapshot location **relative to the snapshot root**. Exit codes follow `reports/__main__.py:39-59` — 0 success, 1 domain refusal, 2 configuration or usage.
- The error surface: `ConfigError` -> 2; `SaveFormatError`, `SnapshotExists`, `SnapshotCorrupt`, `SnapshotDateMismatch`, `UndecodedRecords`, `IngestRunExists`, `ConcurrentLandingError`, `LoadError` -> 1 with `type(error).__name__: message`, so a moved record layout or a mixed snapshot reads as a refusal rather than a traceback. The version guard needs no new code — `parser/header.py` already refuses a non-25 header on both the snapshot and the per-file provenance path.
- `tests/fixtures/warehouse.py::landed_probe` re-pointed onto `read_save` while keeping the three powers that must stay test-only and visible: the temporary snapshot root, `ingest_seq=None` (warehouse-allocated, because a temp directory always says 1), and `purge_snapshot`. None of those moves into `src/`, which answers Open Question 4.
- `tests/test_read_only.py`'s three AC11 legs re-pointed onto `read_save`, with the docstring updated to say the guard now brackets the operator's own path and why landing still stays outside it.
- `tests/test_ingest_command.py` — a new module with an offline half that runs in CI and a `gamedata` half that runs against the **probe** only, per SD-20.
- README.md: the gap blockquote (lines 128-134) deleted, the command added to the setup block beside the two existing ones, and a line noting that the first run creates the declared tables. `/update-docs` then owns whether CLAUDE.md's status paragraph needs the same edit.

### Risks

- **The re-run default is the expensive decision, not the diff.** Whatever this command does on a habitual second invocation becomes the contract `incremental-loading` writes its operator procedure against, and changing it later invalidates a written-down routine. Getting it wrong in the permissive direction costs ~46 MB and ~301,000 rows per accidental run with nothing raised; in the restrictive direction it blocks the free-agent-signed-without-simming case that ADR 0021 exists to serve.
- **Snapshot-sequence and warehouse-sequence can drift, and the command is where they meet.** `take_snapshot` allocates from the filesystem (`snapshot.py:146-164`), `land_snapshot(ingest_seq=None)` allocates from the warehouse (`warehouse/ingest_run.py:137-153`). A landing that fails after the copy leaves a numbered snapshot directory with no run row, so the next run's filesystem sequence is ahead of the warehouse's. Passing the filesystem sequence explicitly keeps the two stores naming the same attempt but leaves visible gaps in the warehouse sequence; passing `None` closes the gaps but makes the snapshot directory and the `ingest_run` row disagree about which attempt they are — which is precisely the disagreement snapshot immutability exists to adjudicate. The plan must state which store is authoritative and why, not discover it.
- **Re-pointing `tests/fixtures/warehouse.py` can silently change its sequence policy.** The fixture snapshots into a temp directory, where the filesystem answer is always 1, and lands with `ingest_seq=None` for that exact reason (its docstring, lines 19-26). If the shared function is written so the CLI's explicit-sequence policy comes along with it, `landed_probe` will start colliding with the first real ingest at seq 1 — and the failure surfaces as `IngestRunExists` in unrelated grain tests, which reads like a warehouse problem rather than a fixture one.
- **AC11 is the most expensive test in the repo and must not get more expensive.** `tests/test_read_only.py:25-28` records 2m35s over 30,703 files and ~6.4 GB hashed three times. Re-pointing its three legs at `read_save` is free; adding the command as a *fourth* bracketed leg would add another full manifest pass, and pulling MySQL inside the diff would let an unrelated database outage silence ADR 0001's guard — the module's own docstring (lines 240-242) rules that out.
- **Absolute paths reaching tracked files.** `saved_games.dat` embeds a user-profile path per save, `ingest.py:25-27` records that the run type deliberately has nowhere to put one, and `gm/` is tracked and public. The command's stdout is the artifact most likely to be pasted into a `gm/decisions/` record, and `tests/test_no_leaks.py` scans tracked and untracked `.md` for drive letters — so a printed absolute snapshot path turns an operator's decision record into a red build. The precedent cuts the other way (`reports/__main__.py:57-58` prints full paths), so this must be a stated choice.
- **The managed league has no automated guard against being the target.** SD-20's probe-first ordering is enforced *inside test modules*; a command with `--save-id` puts the managed league one flag away in a shell the operator types by hand. The command inherits ADR 0001's structural protection (nothing under `src/` opens a game file for writing, and `config.reject_inside_game_roots` fences the write roots), but there is no confirmation step and the scope does not propose one — the plan should decide whether that silence is acceptable.
- **Two 'first production caller' functions are adjacent and tempting.** `saves.assert_challenge_mode` and `snapshot.verify_snapshot` both have only test callers today and both docstrings anticipate this command. Adopting `assert_challenge_mode` as a *refusal* would break ingestion of the retained standard-mode truth save, which `tests/test_parser_vs_export.py` and AC11's second leg both depend on.
- **Scope creep toward `incremental-loading`.** 'What does this save already hold?' is genuinely useful on the refusal path and is also a named outcome of the neighbouring request. Anything beyond naming the landed dates in an error message belongs there.
- **`.env` and the warehouse can disagree about the universe.** `--save-id` resolves against `.env`'s three slots, so an operator who edits `OOTP_LEAGUE` between landings changes which save a bare invocation targets while `reports render --save-id` keeps reading the old key. `reports/resolve.SnapshotRef` already prefers the landed `human_team_id` over configuration for the same reason; the command should print the resolved id rather than assume the operator knows it.

### Open questions

- Does the deliberate-second-look flag refuse-by-default on the date (core) or refuse-only-when-the-bytes-are-identical (the digest pre-flight enhancement)? The second is strictly better behaviour and strictly more build; the operator should pick, because it is their habit being encoded.
- What is the flag called, and does the refusal get its own exit code? `--again` reads well in a procedure; `--new-look` matches ADR 0021's vocabulary ('a second look at the same in-game date').
- Does `ensure_tables` stay implicit on every run, or become an explicit `python -m ootp_ai.warehouse init` that the README's setup block calls once? Implicit is fewer steps for a fresh clone; explicit keeps schema creation a visible act rather than a side effect of landing.
- Should the command refuse to target the managed league without a confirmation flag, given SD-20's probe-first ordering is enforced only inside test modules and this puts `OOTP-AI.lg` one CLI flag away?
- Is `land` the right subcommand name, or should the single verb be implicit as in `python -m ootp_ai.catalog`? `reports` takes a subcommand because it will grow verbs; `warehouse` plausibly will too (`init`, `land`), which argues for keeping it.
- Should stdout name the snapshot location at all? Omitting it entirely is the strictest reading of ADR 0006; a root-relative form is the compromise this scope proposes; the full path is what `reports render` already prints.

### Enhancements proposed

- **Refuse only when the save's bytes are unchanged, using the digests the warehouse already stores** — _grows-build_ — The blunt default above refuses any second landing at a date until the operator learns the flag — which also refuses the legitimate case ADR 0021 was written for: the operator signs a free agent without simming, so the sim date has not moved but `players.dat` has. `ingest_run.source_files` already carries `{name, size, sha256}` per snapshot file (`warehouse/ingest_run.py:180-191`) and `read_ingest_run` decodes it, so 'have the bytes changed since the last landing of this save?' is answerable *before* anything is copied, by digesting the five `SNAPSHOT_FILES` in place. That splits the two cases exactly right: identical bytes -> refuse a no-op; changed bytes -> land the next sequence and say why. It is the better answer to Open Question 3, and it needs its own decision about partial matches (three files identical, two changed) plus tests, which is why it is not in core.
- **A distinct exit code for the append-only refusal** — _cheap_ — `incremental-loading` will write an operator procedure against this command, and 'already landed' is a different outcome from 'the parser refused' or 'MySQL is down' — a procedure that has to grep stderr to tell them apart is a procedure that will get it wrong. Reserving 3 for the refusal costs one constant and one assertion; the existing 0/1/2 precedent stays intact for everything else.
- **Print the save's mode, from `saves.is_challenge_mode`** — _cheap_ — `src/ootp_ai/saves.py:11-15` says the mode check is 'cheap enough to run on every ingest, which matters more here than anywhere else in the pipeline' — and there has never been an ingest to run it on; the only callers are tests. One stat call names whether the landing came from a Challenge-mode save. It must **report, never refuse**: the retained truth save is deliberately standard-mode (`tests/test_cross_mode_format.py:119` asserts exactly that) and is routinely ingested, so an unconditional `assert_challenge_mode` would break a supported path.
- **Re-verify the snapshot after landing with `verify_snapshot`** — _cheap_ — `snapshot.py:254-260` describes itself as 'called after landing a snapshot', and it has no production caller either. Re-digesting ~46 MB costs about a second on a run that already spends ~2.2 s parsing, and it closes the loop the whole snapshot design rests on — if the warehouse and the snapshot ever disagree, the snapshot is right, which is only true if the snapshot was proved intact at landing time.
- **Emit one machine-readable line of the run** — _cheap_ — ADR 0011 tracks GM memory in git and `open-front-office`'s scope (§634) already pins that a journal entry cites a `(save_id, sim_date, ingest_seq)` triple rather than a pasted result set. A single JSON line — triple, row counts, parse seconds, no path — is what a `gm/decisions/` record and `incremental-loading`'s procedure both want to capture, and it is trivially assertable in a test.
- **`land --list` (or a bare `land` with no landing) that names what the warehouse already holds for the target** — _cheap_ — `reports/resolve.landed_sim_dates` already answers 'what dates does this save hold' from `ingest_run` rather than from a directory listing. Surfacing it on the refusal path makes the refusal actionable in the same way `_nothing_landed_message` does for the render path. It edges toward `incremental-loading`'s 'what does this universe hold, and at which dates?' outcome, so it should be flagged as a boundary crossing rather than absorbed silently.

## Scoper: `ambitious`

**Fit verdict:** `clean`

This is a new entry point over library code that is already built, already under test, and already documented — no parser change, no new landed data, no new dataset, and no ADR contradicted. The pattern to copy exists and names itself as such: `src/ootp_ai/reports/__main__.py:1-11` records that entry points are deliberate and sets the shape (resolve settings, resolve the target explicitly, act, print the triple), and `catalog/__main__.py` already followed it once. ADR 0021's append-only semantics are surfaced rather than renegotiated, because `land_snapshot` (`warehouse/load.py:195-250`) already offers exactly the two operations the ADR names and the command only has to choose a default between them. The one genuinely structural decision — where the module lives, since `ootp_ai.ingest` is a 502-line module and `python -m ootp_ai.ingest` cannot host a `__main__` without restructuring — is forced into the open by CLAUDE.md's ban on speculative directories, which is why this is a scoping decision rather than a default. Two things make the fit better than the request assumed. First, the write-allowlist entry the request budgets for is probably not needed at all: `_writes_in()` at `tests/test_read_only.py:348-358` scans a module's own source text for `CREATIVE_CALLS` and write-mode opens, so an entry point that delegates every file creation to `snapshot.py` leaves `WRITERS` (`tests/test_read_only.py:303-317`) untouched — a stronger outcome than allowlisting. Second, the gap is measurably wider than the request states: `ensure_tables` (`warehouse/load.py:169`) has exactly one caller in the entire repo, `tests/fixtures/warehouse.py:93`, and `ops/mysql-bootstrap.sql` creates databases, the app user and grants but no tables — so on a fresh machine the test suite creates the schema as well as filling it.

### Goals

- Give the operator one documented, supported command that takes a save from disk to a landed bronze snapshot — snapshot, verify, parse, land — and prints the `(save_id, sim_date, ingest_seq)` triple it created, so a landing and a later `reports render` can be tied together in a `gm/decisions/` record.
- Make a fresh clone runnable without `pytest`: `uv sync` → `mysql < ops/mysql-bootstrap.sql` → one ingest command → `uv run python -m ootp_ai.reports render` produces a roster page. This requires the command to call `ensure_tables` (`warehouse/load.py:169`), whose only caller today is `tests/fixtures/warehouse.py:93`.
- Stop the test suite being the ingestion path: `tests/fixtures/warehouse.py`'s `landed_probe` (:133-157) calls the same function the operator's command calls, so the two cannot drift, while the fixture's extra powers (temporary snapshot root, warehouse-allocated sequence, `purge_snapshot` at :99) stay under `tests/` where `warehouse/load.py:69-75` requires them.
- Settle the operator-facing append-only default that `incremental-loading` will write its procedure against, and settle it so that ADR 0021's refusal and its next-sequence allocation are both reachable and neither is the wrong thing to hit by habit.
- Extend ADR 0001's manifest-diff proof (`tests/test_read_only.py:223-269`) to bracket the code path the operator actually runs, without pulling a MySQL dependency into the one test this project cannot afford to lose.
- Turn three already-built, currently-uncalled safety functions into production callers: `saves.assert_challenge_mode` and `saves.is_challenge_mode` (`src/ootp_ai/saves.py:81-103`) and `snapshot.verify_snapshot` (`snapshot.py:254`) have zero callers anywhere in `src/` today, and each one's own docstring asserts it is used on every ingest or after every landing.
- Leave `tests/test_read_only.py`'s `WRITERS` allowlist unwidened, by keeping every file creation inside `snapshot.py`.
- Replace README.md:128-134 — the blockquote that documents the absence of this command — and correct `reports/resolve.py:180-182`, whose refusal message already tells the operator to "run the ingest before rendering", naming something that does not exist.

### Non-goals

- Rendering. `uv run python -m ootp_ai.reports render` is the render entry point and stays so (ADR 0016; operator's disposition at intake was "just landing"). At most this scope adds a two-command recipe to README, never a `--then-render` flag.
- The sim-forward-and-re-land procedure and the two-date proof. Both are `incremental-loading`'s (`requests/feature-requests/incremental-loading/FEATURE_REQUEST.md`). This request builds the vehicle only.
- Any change to landing semantics. No upsert, no fix-in-place, no `--force` that overwrites a triple (ADR 0021 §3, and the AST scan it names). The command exposes `IngestRunExists` and the next-sequence allocation; it does not add a third behaviour.
- Anything that writes to a save, automates the game, or reads an in-game screenshot as truth (ADR 0001, ADR 0002).
- Scheduling, watching, daemonising or cron. The operator decides when a save is worth landing.
- A `[project.scripts]` console entry point. `uv run python -m ootp_ai.<package>` is the established invocation for both existing commands and `pyproject.toml` has no `[project.scripts]` today.
- A retention or pruning policy. ADR 0021 records that none exists and ADR 0018 records the monotonic growth as knowingly accepted; making landing easy makes that arrive sooner, which is a finding to state, not a policy to write here.
- Cross-snapshot reads or any diff between two landings — `incremental-loading` owns that seam.
- Building on `flag_save_completed.dat` or any other unwalked file. `docs/data-access.md` §1 labels the content of all fourteen unwalked `.dat` files `assumed`; acting on an assumed label is what this repo's own label table forbids.

### Core scope

- **One operator verb, patterned on the existing entry point.** `uv run python -m ootp_ai.ingest land` — argparse with one subcommand, a `main(argv) -> int` returning `reports/__main__.py`'s exit-code convention (2 for configuration, 1 for a resolvable refusal, 0 for success; `reports/__main__.py:39-59`), and a library-callable `land()` function beside it mirroring `render()` at `reports/__main__.py:62`. The library function is what the test fixture and the read-only guard call; `main()` is what the operator types.
- **Module placement decided, not defaulted (request open question 2).** Recommended: promote `src/ootp_ai/ingest.py` to a package `src/ootp_ai/ingest/` whose `__init__.py` is today's module moved verbatim, plus `ingest/__main__.py`. Every existing importer keeps `from ootp_ai.ingest import …` unchanged — `warehouse/load.py:90`, `warehouse/ingest_run.py:57`, `tests/test_read_only.py:46`, `tests/fixtures/warehouse.py:43`, `tests/test_snapshot_semantics.py:73`. The two alternatives are worse for stated reasons: `warehouse/__main__.py` would name the whole operation after only its last third, and a top-level `ootp_ai/__main__.py` introduces a third invocation convention the request explicitly declines to introduce.
- **Target resolution by configured save role, not by warehouse `save_id`.** `reports render --save-id` (`reports/__main__.py:140-144`) takes a warehouse key; ingest needs a `SaveRef` — a league name plus a root — which `.env` supplies as `managed` / `truth_save` / `probe_save` (`config.py:99-108`, `.env.example:22-40`). So the flag is `--save managed|probe|truth`, defaulting to `managed`. This is a real divergence from the pattern and must be documented as one, because two flags that look alike and mean different things is how the wrong universe gets landed. It also makes SD-20's rehearse-on-the-twin-first rule a single word.
- **`ensure_tables` called by the command.** Measured: `warehouse/load.py:169`'s only caller in the repo is `tests/fixtures/warehouse.py:93`, and `ops/mysql-bootstrap.sql` creates the three databases, the application user and its grants but no tables. Without this, the request's own observable signal — an empty warehouse, one command, then a rendered roster — cannot hold. `ensure_tables` creates and never replaces (`warehouse/load.py:176-178`), so this adds no migration path.
- **The append-only default settled, and open question 3's tension dissolved rather than traded.** The command passes the *snapshot directory's own* `ingest_seq` to `land_snapshot` — the explicit-integer branch documented at `warehouse/load.py:203-211`, which keeps the filesystem and the warehouse naming the same attempt so a cited triple resolves to bytes on disk. Because `take_snapshot` already allocates the next free filesystem sequence (`snapshot.py:189-191`), an operator who re-runs the command by habit gets a *new* snapshot at seq N+1 and a clean landing: the refusal is simply unreachable on the fresh-snapshot path. `IngestRunExists` stays reachable only through `--from-snapshot` or an explicit `--ingest-seq`, where it means exactly what ADR 0021 §1 says it means.
- **No file write in the new module.** Every file creation stays in `snapshot.py`; the entry point prints to stdout and nothing else. Consequence: `WRITERS` at `tests/test_read_only.py:303-317` does not widen, and the guard's own comment about a bare `__main__.py` releasing every `__main__.py` in the tree stays a historical note rather than a live problem.
- **Output contract: the triple, the counts, the cost, and no absolute path.** Print `(save_id, sim_date, ingest_seq)`; the per-table row counts from the returned `IngestRun.row_counts`, which `warehouse/load.py:287-317` establishes by counting back out of the schema rather than restating the builder; `parse_seconds`; and the snapshot location expressed **relative to the configured snapshot root**. Never an absolute path: this output is the artifact most likely to be pasted into a tracked `gm/decisions/` record, and `ingest.py:25-27` records that the run type deliberately has nowhere to put one (ADR 0006).
- **`tests/fixtures/warehouse.py` re-pointed.** `landed_probe` (:133-157) calls the CLI's `land()` function with a temporary snapshot root and warehouse-allocated sequencing, instead of composing `parse_snapshot(take_snapshot(...))` and `_land` by hand. `purge_snapshot` (:99) and the loud-skip helpers (:59-96) stay in `tests/` unchanged — the fixture keeps its extra powers without those powers becoming production surface (request open question 4).
- **ADR 0001's guard extended to the operator's path (request open question 5).** `tests/test_read_only.py:223-269` currently brackets `parse_snapshot(ingest_save(...))` composed by hand. It is amended to drive the entry point's own function in a land-free mode across the same three saves in the same SD-20 order. Landing stays excluded, for the reason the test's own docstring gives at :240-242 — a warehouse outage must not be able to silence this test.
- **Documentation trued up.** README.md:128-134's "There is no ingest command" blockquote is deleted and the setup block at README.md:110-118 names the real command; `reports/resolve.py:180-182` stops referring to an ingest that does not exist; CLAUDE.md's project map and `requests/feature-requests/README.md`'s Index row are updated if `ingest.py` becomes `ingest/`.

### Risks

- **Promoting `ingest.py` to `ingest/` is a 502-line move** that git may record as delete+add rather than a rename, and several tracked references point at the old path by line number — this very request cites `src/ootp_ai/ingest.py:436`, CLAUDE.md's project map names the file, and `tests/test_agent_contract.py` / `tests/test_doc_links.py` may pin paths. Every reference must be found before the move, not after.
- **The retry behaviour differs between the two `land_snapshot` branches, invisibly.** `warehouse/load.py:233-250` retries a deadlock `LANDING_ATTEMPTS` times *and re-allocates the sequence each time*, which only works on the `ingest_seq=None` branch. The core scope's chosen default passes an explicit sequence, so a retry re-attempts the same number and will refuse rather than recover. The command therefore has weaker contention behaviour than the fixture it replaces, and nothing currently surfaces that.
- **Re-pointing the fixture couples ~10 gamedata tests to one new function.** A defect in `land()` now reds `test_snapshot_semantics.py`, `test_grain_contracts.py` and `test_bronze_landing.py` at once instead of one module. The fixture's loud-skip discipline (`tests/fixtures/warehouse.py:82-96`, *"Never a vacuous pass"*) must survive the re-point unchanged, or a MySQL outage starts reporting the grain as holding.
- **A `--snapshot-root` flag is the project's second operator-typed write root**, and `catalog/__main__.py:118-134` records that the first one (`--docs-root`) shipped entirely unvalidated and would have created files under a Challenge Mode save on a plausible tab-completion slip. Forgetting `reject_inside_game_roots` here repeats a known incident.
- **Making landing one command accelerates a cost nobody has bounded.** ADR 0021 records `bronze_name` re-landing 264,095 rows per snapshot with *"no retention policy exists"*; ADR 0018 §Notes leaves the per-date growth rate `unconfirmed`. The feature is correct and the growth is a consequence of it, but the consequence should be stated in the scope rather than discovered on a full disk.
- **`ingest status` overlaps `incremental-loading`'s stated outcome** (*"Anyone reading the warehouse can answer what does this universe hold, and at which dates"*). If both requests build it, one is wasted; if neither does because each assumed the other, the capability is lost. The boundary needs an explicit sentence in whichever scope keeps it.
- **The refusal path is easy to under-test.** `IngestRunExists` is unreachable on the fresh-snapshot path by design, which is the good news — and it means an acceptance suite that only ever runs the happy path never exercises ADR 0021's central guarantee through the new command. The `--from-snapshot` criterion exists specifically to prevent that, and dropping `--from-snapshot` from scope would also drop the only cheap way to reach the refusal.
- **Challenge-mode pre-flight can refuse a legitimate target.** The retained truth save is standard-mode by design (`.env.example:26-30`) and is snapshotted and parsed on every `-m gamedata` run (`tests/test_read_only.py:258-266`). A pre-flight that refuses it without an opt-out breaks an existing, sanctioned workflow.
- **`verify_snapshot` after copy costs a second full digest of ~55 MB** on top of the copy's own before-and-after digests (`snapshot.py:307-313`). It is probably fine against a ~2.2 s parse, but it is unmeasured, and an unmeasured cost added to the operator's most frequent command is how a flag gets disabled and never re-enabled.

### Open questions

- **Where does the module live?** Package promotion of `ingest.py` → `ingest/` (recommended above), `warehouse/__main__.py`, or a top-level `ootp_ai/__main__.py`. CLAUDE.md forbids defaulting into a directory, so this needs a decision recorded with its reason.
- **Is the target named by `.env` role (`--save managed|probe|truth`) or by a free-form league name?** `reports render --save-id` is a warehouse key; an ingest target is a `SaveRef`. Two similarly-named flags meaning different things is a real hazard, and naming them apart is cheaper than documenting the difference.
- **When `--from-snapshot --allocate-seq` runs, the landed `ingest_seq` no longer matches any snapshot directory's sequence.** That is exactly the correction ADR 0021 describes, and it breaks the filesystem↔warehouse correspondence the default is chosen to preserve. Is that acceptable, and must the output say so explicitly every time it happens?
- **Does `ensure_tables` belong inside `land`, or in its own `ingest init` verb?** Creating declared tables as a side effect of a landing is what makes the fresh-clone story work, and it is also schema DDL happening without anyone deciding. `warehouse/load.py:176-178` already refuses to repair a drifted table, so the risk is bounded — but the ergonomics-versus-explicitness call is a real one.
- **Should the command refuse a standard-mode save by default (ADR 0003), given the retained truth save is legitimately standard-mode and is parsed on every gamedata run?** If yes, `--allow-standard-mode` must exist from day one or an existing workflow breaks.
- **Does the per-landing growth measurement belong here or in `incremental-loading`?** ADR 0018 §Notes says the first landed snapshot makes it measurable; this command is what makes landings routine. Either answer is defensible; leaving it unassigned means neither request takes it.
- **Where exactly is the boundary with `incremental-loading` for `ingest status`?** That request lists "what does this universe hold, and at which dates" as one of its own outcomes. If this scope keeps the disk-side half (what saves exist, at what sim date, per `saved_games.dat`) and leaves the warehouse-side half there, that split should be written into both requests.
- **Does the `--no-land` mode need its own name in the read-only guard, or is calling the library function enough?** Question 5 of the request asks whether AC11's proof brackets the operator's path. Calling `land(..., land=False)` brackets the same function `main()` calls but not `main()` itself — argument parsing, settings resolution and the pre-flights sit outside the bracket. Whether that residue matters is a judgement worth making explicitly rather than by default.

### Enhancements proposed

- **`--from-snapshot <dir>`: re-land an already-copied snapshot without re-reading the game** — _cheap_ — This is the exact correction workflow ADR 0021 names — *"A parser fix re-lands the same snapshot at the next sequence, and both readings stay on disk"* — and today no entry point can perform it. Without it, correcting a landing means re-copying ~55 MB from the game (avoidable contact with the one tree ADR 0001 protects) and consuming a filesystem sequence for bytes already on disk. The composition already exists: `snapshot.read_manifest` (`snapshot.py:219`) rebuilds a `Snapshot` from a directory, and `ingest.dump_parse` (`ingest.py:281-300`) already does exactly `_serialize(parse_snapshot(read_manifest(path)))`. Pairs with `--allocate-seq` for the correction case, where the snapshot's own sequence is already claimed.
- **`--no-land`: snapshot and parse, stop before MySQL** — _cheap_ — Listed in the request as a "not now" nicety; it is actually load-bearing. It is what lets ADR 0001's manifest-diff guard bracket the operator's real command without pulling a warehouse dependency into it — `tests/test_read_only.py:240-242` states outright that landing is excluded so an unrelated MySQL outage cannot silence the guard. It also gives the operator a way to prove a save parses cleanly (`check_decoded`, `check_sim_dates` at `ingest.py:235-278`) before committing ~301,000 rows, and gives CI-less machines something to run.
- **Challenge-mode pre-flight via the already-built `saves.py`** — _cheap_ — `src/ootp_ai/saves.py` has **zero callers anywhere in `src/`** — only tests — despite its own docstring at :11-15 saying the mode check is *"cheap enough to run on every ingest, which matters more here than anywhere else in the pipeline: the managed league runs in Challenge Mode, its save carries an integrity hash, and one write destroys it irreversibly."* The ingest command is the caller that sentence was written for. `assert_challenge_mode` on the managed target, with `--allow-standard-mode` for the retained truth save, which is legitimately standard-mode (`.env.example:26-30`) and is routinely parsed (`tests/test_read_only.py:258-266`).
- **`verify_snapshot` called after the copy** — _cheap_ — Same shape of finding: `snapshot.verify_snapshot` (`snapshot.py:254`) has zero callers in `src/`, while its docstring claims it is *"Called after landing a snapshot and again by any consumer that wants to know the bytes it is about to parse are the bytes that were copied."* That sentence is currently false. Making it true costs one re-digest of ~55 MB and turns the snapshot-versus-warehouse triage argument (ADR 0021 Context) from a design intention into something the command actually exercises. Should be defaultable off (`--no-verify`) if the second digest measurably hurts.
- **`--json` machine-readable output** — _cheap_ — Emits the triple, per-table row counts, per-file residual bytes and `parse_seconds` as one JSON object. Complements the core output rather than replacing it: acceptance tests then assert against a parsed object instead of scraping prose, and `incremental-loading` — which has to write a repeatable operator procedure against this command — gets a stable contract rather than a print format. Must carry the same no-absolute-path rule as the human output.
- **An `ingest status` verb: what is on disk, what is landed, and at which dates** — _grows-build_ — Joins three things that already exist and have never been shown together: `saves.enumerate_saves` (`saves.py:69`, which correctly skips the stray empty `.lg` directory), `parser/saved_games.read_saved_games` (`saved_games.py:146`) for each save's own sim date, and `reports/resolve.landed_sim_dates` (`resolve.py:78`) for what the warehouse holds. That last one's docstring already says it is exposed because *"what does the warehouse hold for this universe is the question anyone reaches for the moment a second snapshot exists."* This is also where `docs/data-access.md` §1's `measured` 2026-08-18 correction earns its keep — `saved_games.dat` is the authority for a save's sim date and the in-game Organization screen is not, a mistake that misnamed three operator screenshots by 11, 4 and 11 days. Boundary risk: `incremental-loading` claims "answer what dates does this universe hold" as one of its outcomes, so the split needs agreeing.
- **Sim-date pre-flight before the 55 MB copy, with a stated duplicate warning** — _cheap_ — Read the save's `teams.dat` header date first (`snapshot.py:285-293` already does exactly this, cheaply) and tell the operator, before any copy: *this save is at 2024-03-07, which already holds landings at seq 1..N — proceeding will create seq N+1*. Then proceed, because append-only permits it. This gives open question 3's "filled the warehouse with duplicate landings nobody meant to make" worry a real answer that never refuses a legitimate second look.
- **`--snapshot-root` override, fenced through `reject_inside_game_roots`** — _cheap_ — Needed by the re-pointed test fixture (which snapshots into a `tempfile.TemporaryDirectory`, `tests/fixtures/warehouse.py:149`) and useful to the operator rehearsing against the twin. It is also the project's *second* operator-typed write root, and `catalog/__main__.py:118-134` records in detail what happened to the first: `--docs-root` shipped with no validation at all, and a tab-completion slip would have created files under a Challenge Mode save. `config.reject_inside_game_roots` (`config.py:215`) is public precisely so this cannot be a second copy of the check.
- **Free-disk pre-flight before copying** — _cheap_ — A snapshot is ~55 MB per landing (`.env.example:42-47`), and `snapshot._copy_one` (`snapshot.py:296-306`) deliberately leaves an incomplete directory behind on failure because this module deletes nothing. A cheap free-space check turns a half-written snapshot into a refusal before the first byte.
- **A `gm/decisions/`-pasteable citation block** — _cheap_ — The request's Desired Outcome asks that a landing and a render be tie-able afterwards in a decision record. Emit the triple plus the per-table digests (`warehouse/load.table_digest`, :540) in a form that can be pasted verbatim into a tracked file — which is also what forces the no-absolute-path rule to be tested rather than intended.
- **Print both sequence allocators when they disagree** — _cheap_ — There are two `next_ingest_seq` functions — `snapshot.py:146` allocates from the filesystem, `warehouse/ingest_run.py:137` from the warehouse — and this command is the first place both are live in one process. `tests/fixtures/warehouse.py:19-26` documents the divergence case explicitly (a temporary snapshot root always allocates 1). Rather than silently picking one, print both whenever they differ; it costs a line and makes the one confusing case self-explaining.
- **`--save all`: land every configured save in SD-20 order** — _grows-build_ — The request lists multi-save under "not now". The argument for reconsidering is that `tests/test_read_only.py:19-23` makes probe-then-truth-then-managed *structural rather than conventional* — "two tests are ordered by collection and collection order is a convention" — and the same reasoning applies to an operator refreshing everything. If it ships, the ordering must be inside one invocation, not documented as three commands run in a suggested order.
- **Spike (not a build item): can the command tell that OOTP is currently running?** — _grows-build_ — `tests/test_read_only.py:213-218` already tells the reader "If OOTP is open, close it" when the manifest diff fires, so a moving save is a known hazard, and a snapshot taken mid-save is a torn copy that `verify_snapshot` would not catch (the source moved, not the copy). Whether `flag_save_completed.dat` indicates this is **`unconfirmed`** — `docs/data-access.md` §1 lists it at 1,010–1,065 B with no walker and content labelled `assumed`. Scope this as a measurement with a written finding and a label, never as a feature built on an assumed claim.
- **Measure and print the per-landing warehouse growth** — _cheap_ — ADR 0018 §Notes leaves the growth rate per sim date `unconfirmed` and says *"The first landed snapshot makes it measurable"*; ADR 0021 records `bronze_name`'s 264,095 rows per landing as the largest unglamorous cost. This command is the thing that makes landings routine, so it is both the natural place to print the number and the reason the number starts to matter. Cheap as a printed figure; explicitly not a retention policy.
- **A two-command README recipe rather than a chaining flag** — _cheap_ — The request rules rendering out of this command, correctly. But the observable signal it names is a landing *followed by* a render, so README should show both lines together — `ingest land` then `reports render` — which delivers the operator outcome without giving this command a second job.

## Scoper: `minimalist`

**Fit verdict:** `clean`

This is an entry point over code that is already built, already tested and already documented — no new landed data, no parser change, no ADR contradiction. Precedent exists twice: `src/ootp_ai/reports/__main__.py` (resolve settings → resolve target → act → print the triple) and `src/ootp_ai/catalog/__main__.py` (same shape, no subcommand). The five dataset contracts are inherited unchanged from the eight tables declared in `src/ootp_ai/contracts/tables.toml` (e.g. `bronze_player` grain 'one row per player per save per snapshot', key `[save_id, sim_date, ingest_seq, player_id]` at tables.toml:222-224); this request lands the same rows through a new caller, so grain / keys / coverage / update semantics / ADR-0005 layer are all untouched and need no re-settling. Parser obligations do not fire either — `PARSED_FILES` (ingest.py:66) is unchanged, no new field is read, and the version guard in `parser/header.py` is reached through the same `take_snapshot` path. Two caveats keep this from being trivial. (1) The request's premise that the command 'surfaces ADR 0021's refusal' is largely vacuous as stated: `take_snapshot` allocates the next FILESYSTEM sequence on every run (snapshot.py:146-164, 189-191), so a habitual re-run normally produces a fresh seq and lands a DUPLICATE rather than hitting `IngestRunExists`. Open Question 3 is therefore asking about a refusal that will rarely fire. (2) Two independent sequence allocators exist — `snapshot.next_ingest_seq` reads directories under a gitignored, disposable `var/snapshots`, `warehouse.ingest_run.next_ingest_seq` reads `MAX(ingest_seq)` from MySQL (ingest_run.py:137-153) — and they are already out of step in this repo because every existing landing came from a `tempfile.TemporaryDirectory()` snapshot (tests/fixtures/warehouse.py:149-151). That is the real design hazard, and it is small enough to settle in scope rather than a reason to reshape.

### Goals

- One documented command takes a configured save from disk to a landed bronze snapshot — snapshot, parse, land — and exits 0 having printed the `(save_id, sim_date, ingest_seq)` triple it created, in the same three facts `reports render` prints so a landing and a render can be tied together in a `gm/decisions/` record.
- That printed output is safe to paste into a TRACKED file: it carries no absolute path, drive letter, home directory or email address (ADR 0006; `ingest.py:25-27` already argues the record type has nowhere to put a path — the command must not reintroduce one on stdout, which is where `reports/__main__.py` deliberately does print paths).
- `README.md`'s setup block names the command and the 'There is no ingest command' paragraph (README.md:128-134) is deleted rather than softened, so a fresh clone goes `uv sync` → bootstrap → command → `reports render` with no `pytest` in the path.
- The command refuses exactly what the library refuses and softens nothing: `IngestRunExists`, `SnapshotExists`, `SnapshotCorrupt`, `SaveFormatError`, `UndecodedRecords`, `SnapshotDateMismatch` and `ConcurrentLandingError` each reach the operator by name with a nonzero exit; there is no `--force` and no overwrite path (ADR 0021).
- Target selection defaults to the managed league and is overridable to one of the other CONFIGURED saves, so SD-20's 'rehearse on the disposable Challenge twin first' is expressible as a flag rather than an edit to `.env`.
- The operator's code path is itself covered by tests, rather than covered by inference from the library tests that exist today — including that its exit codes follow the established convention (2 = configuration/usage, 1 = a refused operation; `reports/__main__.py:43,55`, `catalog/__main__.py:108,111`).

### Non-goals

- Rendering anything. `reports render` is the render entry point; this command lands and prints and stops (operator's disposition at intake).
- Subcommands or flags for snapshot-only, parse-only, or `--dry-run`. The library already separates those three acts (ingest.py:436-460, 161-217) and no caller has asked for them apart; adding CLI surface for a split nobody uses is the definition of speculative.
- A `--force`, `--overwrite`, `--ingest-seq` or `--snapshot-root` flag. The first two contradict ADR 0021; the last two exist only to serve tests, and a keyword argument on the library function serves tests without becoming operator surface.
- A new entry in `WRITERS` in `tests/test_read_only.py:303-317`. The guard scans a module's own SOURCE TEXT for creative calls (`_writes_in`, lines 337/348-358) — a command that delegates every write to `snapshot.py` (`snapshot_dir.mkdir(parents=True)` at snapshot.py:205 already creates all three levels) trips nothing. Adding an entry would widen ADR 0001's allowlist to buy nothing. This directly contradicts the request's Scope Signals ('the writer-allowlist entry the new module needs') and the contradiction is deliberate: verify at build time, and only add an entry if the module genuinely acquires a write.
- Extending the AC11 gamedata manifest diff (`tests/test_read_only.py:223-269`) to run the landing command. That module's own docstring already argued the case against it: 'Landing is deliberately not included: it writes to MySQL, not to the game, and pulling a warehouse dependency into ADR 0001's guard would let an unrelated outage silence the one test the project cannot afford to lose' (lines 240-242). The new module is covered for free by the STATIC half of the same file, which rglobs all of `src/ootp_ai/`. Open Question 5 is answered 'no, and here is the existing argument'.
- A challenge-mode pre-flight. `saves.assert_challenge_mode` exists and is called by nothing in `src/`; wiring it in would refuse the standard-mode truth save, which `test_read_only.py:263` ingests legitimately. Reading is read-only regardless of mode, so the check protects nothing here.
- Landing more than one save per invocation, progress output for the ~2.2 s parse, or any scheduling, watching or daemon.
- A `[project.scripts]` console entry point. `uv run python -m ootp_ai.<x>` is the established invocation for both existing commands.
- Any change to landing semantics, to `land_snapshot`, to `contracts/`, or to the eight declared tables.
- Cross-snapshot reads, a two-date proof, a sim-forward procedure, or retention/pruning — all owned by `requests/feature-requests/incremental-loading/` (its Scope Signals claim them explicitly).
- Hardening the snapshot against a mid-write save (a re-digest of every source after the last copy). Real, but it is a pre-existing property of `take_snapshot`, applies equally to today's test-driven path, and is not what this request is for.

### Core scope

- ONE command, no subcommand — matching `catalog/__main__.py:2-4`'s argument ('No subcommand, deliberately … This command has one job'). It snapshots, parses and lands in one act. Open Question 1 is settled: one command; the library keeps the three-way split for callers, and the CLI does not mirror it.
- It lives in a PACKAGE, not in `ingest.py`. Recommended: promote `src/ootp_ai/ingest.py` to `src/ootp_ai/ingest/__init__.py` plus `src/ootp_ai/ingest/__main__.py`, which keeps every existing `from ootp_ai.ingest import …` working (13 call sites across `src/` and `tests/`, verified by grep) and reuses the established `python -m ootp_ai.<package>` invocation. Correcting the request's Open Question 2: `python -m ootp_ai.ingest` DOES work on a plain module, but running a 500-line library module as `__main__` double-imports it under two names, producing two distinct `IngestRun`/`ParsedSnapshot` classes across the boundary — a silent `isinstance` hazard. That, not a restriction of `-m`, is the reason to promote. No markdown link anywhere targets `src/ootp_ai/ingest.py` (verified), so `tests/test_doc_links.py` is unaffected; stale prose in `first-sight` handoffs is historical record and stays.
- A thin library function beside `main()` — the `render()`/`generate()` pattern (`reports/__main__.py:62`, `catalog/__main__.py:162`) — that takes `settings`, an optional save selector and an optional `ingest_seq`, and returns the `IngestRun`. `main()` is argparse, error-to-exit-code mapping and printing, and nothing else. `tests/test_reports.py:94-106` is the precedent for testing the entry point through this function rather than by subprocess.
- `--save-id`, defaulting to the managed league, RESOLVED AGAINST THE CONFIGURED SAVES ONLY. `Settings` exposes exactly three `SaveRef`s — `managed`, `truth_save`, `probe_save` (config.py:100-108) — and there is no save_id→SaveRef map anywhere in the repo. `reports render --save-id` takes a warehouse key, not a disk locator, so naive symmetry produces a flag that cannot find a save. Match the argument against `SaveRef.save_id` for the configured refs; on no match, exit 2 listing the ids that are configured. No `enumerate_saves` sweep of the saved-games root — that would let a typo ingest an unrelated league.
- The seq the command claims: pass the SNAPSHOT'S OWN `ingest_seq` explicitly to `land_snapshot`, which is what `load.py:206-213` prescribes when a durable snapshot is the artifact the row should point at, and which keeps the two stores naming the same attempt. Do NOT pass `None` from the CLI: warehouse-side allocation is for transient snapshots and would let the landed triple and the snapshot directory carry different numbers, breaking the 'if the two disagree, the snapshot is right' triage ADR 0021 rests on.
- Settling Open Question 3 (the operator-facing default): the command has NO auto-allocate flag and NO `--force`. A landed triple refuses by name and exits nonzero; a genuine second look at an unchanged date is served automatically, because `take_snapshot` already allocates the next filesystem sequence on every run. State plainly in the command's docstring and in `README.md` that a repeat run therefore normally LANDS AGAIN rather than refusing — see risk 2; do not let the docs imply a protection that is not there.
- Exit-code discipline: 2 for configuration and usage errors, 1 for a refused operation, 0 on success — mirroring both existing entry points. Catch the refusal exceptions EXPLICITLY by name; `IngestRunExists`, `SnapshotExists`, `SnapshotCorrupt`, `NotChallengeMode`, `SaveFormatError`, `UndecodedRecords`, `SnapshotDateMismatch` and `ConcurrentLandingError` share no base class, so a tuple that misses one turns a refusal into a traceback. `ConcurrentLandingError` must be reported as its own thing — `load.py:146-154` warns specifically that telling an operator 'already landed' when the truth is 'another loader is writing' sends them looking for a landing that never happened.
- Prints the triple, and NOT the snapshot directory. This is the one place the command deliberately diverges from `reports/__main__.py`, which prints paths (line 58): an ingest run's output is the artifact most likely to be pasted into a tracked `gm/decisions/` record, and `saved_games.dat` embeds a user-profile path per save (ingest.py:25-27, ADR 0006). Also print the per-table row counts, which are already read back out of the schema inside the landing transaction (`load.py:287-317`) and cost nothing extra.
- `README.md`: replace the setup block's ingest-gap paragraph (lines 128-134) with the command, in the same fenced block as `reports render` and `catalog` (lines 117-118). `CLAUDE.md`'s Status paragraph and its `src/ootp_ai/` map entry need a truthing pass through `/update-docs` in the same change.
- The tests named in the acceptance criteria above. Nothing else.

### Risks

- THE PREMISE RISK, and the biggest one. The request says the command 'surfaces' ADR 0021's refusal. It largely cannot. `take_snapshot` allocates the next FILESYSTEM sequence on every run (snapshot.py:146-164, 189-191), so an operator who re-runs the command out of habit gets a new seq that is not landed, and lands a full duplicate — ~301,000 rows, ~264,095 of them `bronze_name` (ADR 0021 measured), plus a 55 MB snapshot, none of it reclaimable. Getting Open Question 3 'backwards' does not mean choosing refuse-vs-allocate; it means shipping documentation that claims a protection the code does not provide. Label: inferred from reading snapshot.py and load.py; not executed.
- TWO INDEPENDENT SEQUENCE ALLOCATORS, ALREADY OUT OF STEP. `snapshot.next_ingest_seq` counts directories under a gitignored `var/snapshots` (snapshot.py:146-164); `warehouse.ingest_run.next_ingest_seq` reads `MAX(ingest_seq)` from MySQL (ingest_run.py:137-153). Every landing now in the warehouse came from a `tempfile.TemporaryDirectory()` snapshot (tests/fixtures/warehouse.py:149-151) that no longer exists, so the two stores are independent by construction. `var/` is documented as disposable and rebuildable; delete it (or clone fresh onto a machine whose warehouse persists) and the command's first run claims seq 1 and hits `IngestRunExists` on a landing the operator never made. It self-heals across repeated runs — seq 2, seq 3 — but burns 55 MB and a full parse per attempt and reads like a broken command. Verified on this machine: `var/snapshots/OOTP-AI/2024-03-07/1` exists; I did not query MySQL, so whether the two currently agree is inferred, not measured.
- THE WRITERS-ALLOWLIST ASSUMPTION IN THE REQUEST MAY NOT HOLD. Scope Signals lists 'the writer-allowlist entry the new module needs' as in-scope. The guard is a source-text scan for `.write_text(`, `.write_bytes(`, `.touch(`, `.mkdir(`, `os.makedirs` and write-mode `open` in the module's OWN text (test_read_only.py:337, 348-358, 361-366) — not a capability model. `snapshot_dir.mkdir(parents=True)` at snapshot.py:205 already builds all three path levels, so a delegating command trips nothing and needs no entry. Adding one anyway widens ADR 0001's allowlist for zero benefit, which is exactly the kind of quiet erosion the list's own comment (lines 296-302) was written to prevent.
- OPEN QUESTION 5 CONFLICTS WITH AN ARGUMENT ALREADY IN THE TREE. Extending the AC11 manifest diff to bracket the landing command pulls a MySQL dependency into ADR 0001's guard; `test_read_only.py:240-242` refuses this in terms: an unrelated warehouse outage would then silence 'the one test the project cannot afford to lose'. The static half of the same module already covers the new file for free (it rglobs `src/ootp_ai/`). Answer 'no' explicitly rather than leaving a plausible-sounding extension for the plan stage to adopt.
- RE-POINTING THE TEST FIXTURE CAN EXPORT TEST-ONLY POWERS INTO PRODUCTION SURFACE — the request's own Open Question 4, and it is a live hazard. `landed_probe` needs a temporary snapshot root, warehouse-side seq allocation (`ingest_seq=None`) and a `DELETE`. The first two are safe as library keyword arguments and unsafe as CLI flags; the third must never move into `src/` (ADR 0021 §3; `load.py:69-74`: 'a delete helper written "just for tests" is how that property quietly stops being true', enforced by the AST scan `test_bronze_landing.py:818`). If the plan re-points the fixture, it must do so without adding a single argparse flag.
- RUNNING A PLAIN MODULE UNDER `-m`. If the entry point is bolted onto `ingest.py` rather than a package, `python -m ootp_ai.ingest` executes it as `__main__` and its own `from ootp_ai.…` imports re-import it as `ootp_ai.ingest` — two module objects, two `IngestRun` classes, `isinstance` false across the boundary. Silent, and it would show up as a mystifying failure in `warehouse/load.py`, which imports `ParsedSnapshot` from that module (load.py:90). Label: inferred from Python import semantics, not reproduced here.
- INGESTING WHILE OOTP IS RUNNING. Partially guarded, not fully: `_copy_one` digests each source before and after the copy so a torn single file raises `SnapshotCorrupt` (snapshot.py:307-318), and `check_sim_dates` refuses a snapshot whose files disagree about the in-game date (ingest.py:235-258). Neither catches a mid-write change ACROSS files at an unchanged sim date. `test_read_only.py:215-216` shows the project already knows the game writes to its own install and saves while open. A CLI makes this reachable outside a deliberate `-m gamedata` run, which is exactly when an operator is least likely to have quit the game first. Related but distinct: `docs/data-access.md:226-227` labels the write-lock question `unconfirmed` — for the SQLite file, not the `.dat` files, so do not cite it as if it covered this.
- THE `--save-id` FLAG HAS NO RESOLVER TO STAND ON. The request says '`--save-id` should probably exist from day one' by analogy with `reports render`, but there that argument is a warehouse key and here it must locate bytes on disk. `Settings` carries three named `SaveRef`s and no lookup by id (config.py:100-108). If this is not settled in scope, the plan will either invent a `saved_games` sweep (letting a typo ingest an unrelated league) or quietly ship a flag that only ever accepts the managed league's own id.
- COST AND IRREVERSIBILITY OF EACH RUN. ~55 MB copied and double-hashed per snapshot (`SNAPSHOT_FILES`, snapshot.py:65-83), a ~2.2 s parse, and one transaction of ~301,000 rows with an eight-table `COUNT(*)` read-back inside it (load.py:287-317). Nothing reclaims either store. An entry point makes it one keystroke to do this repeatedly, which is the whole reason risk 1 matters.
- CONFLATING CONTENTION WITH A REFUSAL. `land_snapshot` retries three times on 1213/1205 and then raises `ConcurrentLandingError` (load.py:139, 233-250). If `main()` collapses that into an 'already landed' message, the operator goes looking for a landing that does not exist — `load.py:146-154` names this failure specifically.
- DOC-TRUTH DEBT IS PART OF THE CHANGE, NOT AFTER IT. `README.md:128-134` currently documents the gap as a feature of the setup; `CLAUDE.md`'s Status paragraph and its `src/ootp_ai/` map line describe two entry points. `/update-docs` is a commit gate here, and a change that ships the command without truthing all three leaves the repo asserting a gap it just closed.
- THE DOWNSTREAM CONTRACT IS BEING PINNED BY THIS DIFF. `requests/feature-requests/incremental-loading/` will write an operator procedure against whatever string this ships (its Desired Outcome asks for 'a written, repeatable procedure' for sim-forward-and-re-land). The invocation string, the flag name, the exit codes and the printed format are all cheap now and expensive after that procedure exists. That, not the size of the diff, is why the request correctly refuses a stage skip.

### Open questions

- Does the duplicate-bytes refusal (enhancement 1) go into core, or ship as documentation of a known hazard? My recommendation is enhancement-and-take-it, because without it the command's advertised ADR 0021 behaviour is close to vacuous — but the stated problem is solved without it and the decider should own that trade.
- Confirm the `ingest.py` → `ingest/` package promotion is acceptable as a `git mv`. It is import-transparent (13 call sites keep working) and breaks no doc-link test (no markdown link targets the file — verified), but it does leave stale prose citations in `.claude/agents/data-engineer-memory.md:202` and several `first-sight` handoffs. Alternatives, both worse in my reading: `warehouse/__main__.py` (the command snapshots and parses, which are not warehouse concerns) and a top-level `ootp_ai/__main__.py` (a bare namespace command that will need subcommands forever, and a third invocation convention).
- Should `--save-id` resolve only among the three configured `SaveRef`s, or enumerate `settings.saved_games` via `saves.enumerate_saves`? I recommend configured-only. The looser option is the one SD-20's 'rehearse against the twin' argument does not need, and it is how a typo reaches a league nobody meant to land.
- Does `tests/fixtures/warehouse.py::landed_probe` get re-pointed in this change or after `incremental-loading` has settled the cross-snapshot read path? Re-pointing is achievable without new CLI surface, but it re-proves two gamedata suites and the request's benefit — the tests stop being the ingestion path — is already delivered the moment the command exists.
- Is there any landed `ingest_run` row for the managed league whose `ingest_seq` collides with what `var/snapshots/OOTP-AI/2024-03-07/` would allocate next? I read the filesystem side but did not query MySQL. One `SELECT save_id, sim_date, MAX(ingest_seq) FROM ingest_run GROUP BY 1,2` before the plan stage turns risk 2 from inferred into measured, and it is the difference between 'the operator's first run works' and 'the operator's first run refuses'.

### Enhancements proposed

- **Refuse a landing whose source bytes are already landed at the same (save_id, sim_date)** — _cheap_ — This is the only thing that makes Open Question 3's protection real. Because `take_snapshot` allocates a fresh filesystem sequence per run, a habitual re-run does NOT hit `IngestRunExists` — it lands ~301,000 duplicate rows at seq+1, permanently, with no retention policy to reclaim them (ADR 0021 'Consequences': 'Storage grows monotonically and nothing here reclaims it: no retention policy exists'). Worse than the disk: `ingest_seq` is supposed to be evidence that the operator took a deliberate second look, and accidental re-runs make it meaningless as evidence — which is the specific thing ADR 0021 exists to preserve. The check is cheap because the material is already there: `ingest_run.source_files` stores per-file sha256 (ingest_run.py:180-191) and `read_ingest_run` already decodes it (ingest_run.py:238-268). Compare the new snapshot's digests against landed runs at the same `(save_id, sim_date)`; on an exact match, refuse and name the seq that already holds those bytes. A named opt-in flag must exist for the legitimate case ADR 0021 calls out explicitly — 'A parser fix re-lands the same snapshot at the next sequence' — where the bytes are identical and the parse is not. I am recommending this as an enhancement rather than core because the stated problem is solved without it, and the decider should get to see the price.
- **Re-point `tests/fixtures/warehouse.py::landed_probe` at the new library function** — _grows-build_ — Satisfies the request's stated wish that the fixture 'calls the same path the operator does, rather than being the path', and closes the drift the request worries about. It is feasible without new operator surface, because the two powers the fixture needs are already expressible: `snapshot_root` is a `Settings` field (the `replace(settings, snapshot_root=tmp)` idiom is already used at `tests/test_read_only.py:193`), and `ingest_seq=None` is already a parameter of `land_snapshot` (load.py:199) that the library function can accept as a keyword WITHOUT an argparse flag. What must not happen is the inverse — inventing `--snapshot-root`/`--ingest-seq` CLI flags so a test can drive the command. `purge_snapshot` (fixtures/warehouse.py:99) stays in `tests/` regardless: it is a DELETE, and ADR 0021 §3 plus `load.py:69-74` are explicit that a delete helper written 'just for tests' inside `src/` is how append-only stops being true. This is graded grows-build because it touches two gamedata suites (`test_grain_contracts.py`, `test_snapshot_semantics.py`) that a green run must re-prove.
- **Print the already-landed sim dates and sequences for the target save before landing** — _cheap_ — `reports/resolve.py` already exposes `landed_sim_dates()`, so the command could open with 'this save currently holds 2024-03-07 seq 1' before it copies 55 MB. It turns the operator's most common question ('did I already do this?') into output rather than a MySQL query, and it costs one existing function call. Deliberately graded as an enhancement and not core: it is convenience, it adds a warehouse round trip before the read-only half of the run, and it partially overlaps the digest guard above — if that ships, this is mostly redundant.
- **An explicit `--yes-managed` style confirmation before the command touches the managed league** — _cheap_ — SD-20 sequences every filesystem-touching operation against the disposable twin first, and the managed league is the target this project has no recovery for. The command defaults to the managed league (for symmetry with `reports render`), which means the safest target is the one you get by typing the least. A confirmation, or an inverted default where `--save-id` is required, would restore that. I am NOT recommending it: the command only ever READS the save (`shutil.copy2` reads the source and writes only the destination, snapshot.py:296-319) and `tests/test_read_only.py` proves the whole pipeline touches nothing under either game root, so the harm a mistyped target can do is a wasted 55 MB snapshot and a landing under the wrong `save_id` — recoverable, and visible in the printed triple. Listed so the decision is on the record rather than absent.
